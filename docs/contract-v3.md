# 载重约束的整单拣货波次 v3

仓配人员已经有 v1 分配器给出的固定结果：哪个订单拿哪个批次的多少数量。本模式不重新决策商业分配，只把这些固定结果编译成仓内可执行的取货与行走清单：先分波，再为每波生成合法的有向行走轨迹与逐次装载。输出是可独立读取的 JSON 快照，不写真实库存，不读取或修改 v2 承诺账本。

- **入口**：`perishable-wave --source JSON --output JSON`（也可 `python3 -m perishable_fulfillment.wave`）。仅 Python 标准库、完全离线。
- **调用关系**：直接调用未修改的 `model.analyze`，保留 v1 的 held 排除、`expires >= as_of`（含到期日）、`(priority, id)` 顺序、逐订单 FEFO 与部分履约/短缺。v1/v2 的 CLI 与行为不变。
- 代码：`src/perishable_fulfillment/wave.py`；测试：`tests/test_wave.py`；样例：`fixtures/wave_input.json`、`fixtures/wave_detour.json`、`fixtures/wave_roundtrip.json`。

## 输入契约

顶层严格为 `{fulfillment, warehouse}`，拒绝未知字段、重复 JSON 键、`NaN/Infinity`；沿用 `common.py` 的 8 MB 字节上限与标识符规则（非空、无首尾空白、无控制字符、≤128 字符）。

`fulfillment` 是原 v1 的完整输入 `as_of/lots/orders`，字段与边界完全沿用 v1；新模式另加更紧的行数上限：最多 **8 订单、64 批次**。

`warehouse` 严格为 `{depot, nodes, edges, lot_nodes, sku_grams, cart_capacity}`：

- `nodes`：最多 32 个唯一标识符；`depot` 必须在其中。
- `edges`：最多 128 条，每条严格为 `{id, from, to, distance, max_load}`。`edge id` 唯一、两端必须存在、不允许自环；允许同端点平行边。**不隐含反向边**。
  - `distance` 为 `1..10^9` 整数。
  - `max_load` 为 `0..10^18` 整数（`0` 表示载货时不可通行，空车仍可通行）。
- `lot_nodes`：`{lot, node}` 数组，必须**恰好覆盖全部源批次各一次**；货位必须存在且不能是 `depot`。
- `sku_grams`：`{sku, grams}` 数组，必须**恰好覆盖源批次与订单出现的每个 SKU 各一次**；`grams` 为 `1..10^9` 整数。
- `cart_capacity`：`1..10^18` 整数。

所有整数都拒绝 `bool`（Python 中 `bool` 是 `int` 子类），拒绝浮点。重复键、重复记录、未知字段一律拒绝。

## 任务与重量

对 `model.analyze` 结果中的每个正数 `allocation`，生成唯一的 `(order, lot, quantity)` 任务：

- 按源 lot 映射 SKU 与货位，重量为 `quantity * grams`；所有乘积与累计重量都用 Python 整数，不截断、不溢出。
- 非任务节点可作为通道；新模式最多 10 个**实际有正任务**的不同货位，超出即拒绝。
- 不生成订单缺货部分的任务，不因路线困难重新选批次；零履约订单不占波，短缺单独保留。

## 分波

- 订单的全部已分配任务必须属于同一波（订单不可拆波）。
- 同一波在同一货位的所有任务合并为**一次整取**，动作仍列出对应的原任务数量；不同波可以分别去同一货位。
- 目标严格分层：先最小化波数，再最小化总距离，再按「排序后的订单组 ID 元组序列」字典序最小，最后按「各波动作签名序列」字典序最小。
- 规范化：每波内订单 ID 升序组成元组，波次按这些元组升序；动作签名为按执行顺序排列的 `("move", edge_id)` / `("pick", node_id)` 二元组序列，用普通字符串字典序比较（不是 JSON 序列化后的字节序）。
- 若某组在有向边载重约束下无法回仓（例如总重量能装进车，但任一段路径的 `max_load` 不够），编译器会拆组；**绝不把仅总重量可行的组当作可行波**。
- 若任一有已分配任务的订单**单独**也无合法路线，整次命令失败并在错误信息中列明这些订单；不会静默漏单或返回部分成功。若所有单订单都可行，则单订单波方案必定可行——某个较大的候选组不可行不会导致整次失败。

## 载重感知路线引擎

给定一组订单，返回从 `depot` 空车出发、取完该组任务并回 `depot` 的合法**最短有向行走**及逐次装载轨迹。途中可重复经过节点，也可重复经过 `depot`。

- 路线状态是 `(节点, 已取货位集合)`；当前载重恰好是已取任务重量之和。
- 边是否可走由**通过该边时的当前载重**决定：载重必须同时 `<= cart_capacity` 且 `<= edge.max_load`（含等号）。
- 每波在同一货位的所有任务只在**一次 pick** 中整取；可延后取货，**路过不自动拾取**；不得按件展开。
- 途中即使经过 `depot` 也不得卸货、补货或丢弃任务；只有取完本波全部任务后才在 `depot` 结束并卸货。不同波之间空车重新出发。
- 路线中的每条 `move` 引用真实 `edge id`；每条 `pick` 标明货位、原任务列表、增量及动作后载重。
- 同一组的路线也按最短距离、再动作签名最小选择。

求解方式：在有限状态图（节点 × 取货子集）上做一次**整数**反向 Dijkstra，得到每个状态到目标的精确最小剩余距离；随后从起点贪心选择「保持最优的最小的动作标签」，即得距离最优且动作签名最小的路线。所有重量、距离与比较都用整数。

> **为什么不是「先求静态最短路线再验重」**：静态最短回边在空车时最短，但装货后可能超重；本引擎把载重编码进状态，能发现更长但合法的绕路。**为什么不是「经过即取」**：先经过某货位不取、从别处取货后再回来整取是合法且更优的业务路线，本引擎把「取或暂不取」作为状态转移。

## 报告契约（schema_version=3）

- 顶层：`schema_version`、`source_sha256`、`fulfillment`（原 v1 分配结果）、`waves[]`、`total_waves`、`total_distance`、`zero_fulfillment_orders`、`shortages`。
- 每波：`orders`（升序 ID）、`tasks`（逐 `(order, lot, quantity)` 任务，含 `sku/node/grams/weight`）、`actions`（完整动作轨迹）、`distance`、`final_weight`。
- 动作：
  - `move`：`{type: "move", edge, from, to, distance, load}`；`load` 是**通过该边时**的载重。
  - `pick`：`{type: "pick", node, increment, load_before, load_after, tasks[]}`。
- `zero_fulfillment_orders`：按 ID 升序；`shortages`：原 v1 短缺，按 v1 输出顺序保留。
- **守恒**：任务合并与动作展开后，每条 v1 分配数量既不能漏也不能多。写出前会完整重放每波动作，核对边拓扑、载重上限、`max_load`、取货合并、每任务唯一性与距离/最终重量；任何不一致都以内部错误失败而非发布报告。

全部零履约时输出 `waves=[]`、`total_waves=0`、`total_distance=0`。

## 失败、发布与幂等

- 输出前完整完成校验和求解；失败退出码 2，保留既有报告。
- 输出不得覆盖输入，包括硬链接指向同一 inode；拒绝输出符号链接。
- 成功时经临时文件 + `os.replace` 原子发布；相同输入重跑得到字节相同的内容（稳定排序）。

## 演示

```sh
python3 -m perishable_fulfillment.wave \
  --source fixtures/wave_input.json --output run/wave.json
```

`fixtures/wave_input.json`：2 波、总距离 18；O4（无同 SKU 库存）零履约，O3 部分履约保留短缺 2。

`fixtures/wave_detour.json`：静态最短回边 `A->D` 限重 1 但需载 2，故绕行 `A->B->D`，距离 5。

`fixtures/wave_roundtrip.json`：`A->B` 限重 0，必须先空车经过 A 到 B 取 1，再回 A 整取 2，总距离 4。

## 设计取舍与边界

- **道路抽象**：有向边、无反向隐含、逐边 `max_load`、可平行、可重复经过节点。真实仓内的单行道、限重巷道、装卸点容量都可映射到这张图上；本模式不建模叉车调度、拥堵、时间窗或拣货员数量。
- **状态空间**：每波最多 10 个实际取货货位，`32 × 2^10` 个状态；分波对最多 8 个订单做集合划分（Bell(8)=4140），每组路线可缓存。这样最坏规模在秒级。
- **不写库存**：本模式是单次作业计划快照，不修改批次可售量、不产生拣货事实、不与 v2 预留交互。重复运行不累加。
- **路线可行性**：载重按「取货后载重」计算；`max_load=0` 的边空车可走、载货不可走。所有已分配订单都单独不可达时整次失败，不返回部分计划。
